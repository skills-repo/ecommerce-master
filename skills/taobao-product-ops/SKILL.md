# 淘宝商品发布与管理（Taobao Product Ops）

> 发布/改价/上下架一条链：**API 优先、浏览器半自动兜底**的双通道设计。核心复用资产是
> 「商品内容包」——结构化 JSON 逐字段对应表单项，无论走 API 还是人工都能直接消费。

## 能力

- 商品内容包（Content Pack）标准结构：标题/类目/属性/图集/详情/定价
- TOP API 发布链路：`taobao.item.add` → `picture.upload` → 类目属性映射
- 无资质/闲鱼场景：内容包 + 浏览器半自动（发布按钮人工点）
- 资质门槛判断：个体工商户 + 企业支付宝 → 企业店铺 → 交易类 API 权限

## 使用方式

```
/taobao-product-ops 生成 Switch 卡带商品的内容包并发布到淘宝
/taobao-product-ops 这批旧货要上闲鱼，帮我出内容包和人工发布清单
/taobao-product-ops 我的店铺资质够不够走 API 发布？
```

## 双通道决策（先判资质，再判渠道）

| 条件 | 通道 |
|------|------|
| 有企业店铺 + TOP 应用已获 `taobao.item.add` 权限 | **A：API 发布**（`item.add` + `itemprops.get` 映射属性，限速重试） |
| 有个体户资质但 API 权限未批（人工审核 3–5 工作日） | 等审批，期间走 B |
| 无资质 / 渠道是闲鱼（无官方商家 API） | **B：内容包 + 浏览器半自动**（执行层用 `ai-fullstack-engineer` 的 `browser-ops`：视觉驱动填表、滑块人工过、发布按钮人点） |

## 商品内容包（核心资产）

```json
{
  "title": "<类目词+品牌+型号+成色+规格，30 汉字内，堆满不堆砌>",
  "category_path": "<一级/二级/叶子类目>",
  "props": {"成色": "95新", "region": "国行"},
  "images": ["主图1", "细节图xN（8 图制）"],
  "detail": "<成色描述+问题 disclosed+配件清单+售后口径>",
  "price": {"anchor": "<市场价>", "ours": "<定价>", "floor": "<底价>"},
  "channel": ["taobao", "xianyu"]
}
```

内容包一次生成、三处消费：API 请求体、browser-ops 填表、人工照抄清单。

## 红线（违反即停）

- **游戏账号/代练/账号租赁类目不得发淘宝**（平台禁售，下架处罚风险）——账号租赁只走闲鱼个人闲置形态
- 不写风控对抗代码；滑块/验证码一律人工兜底（见 `browser-ops` playbook）
- 类目/属性如实填写；批量上架走 API 限速，不做铺货式群控

## 限制

- API 通道需个体工商户资质、企业支付宝、自用型应用 + 交易类 API 权限（高级权限 3–5 工作日人工审核），交易类 API 可能需保证金
- TOP 有 App 级与 API 级限流；批量上架必须限速 + 重试退避
- 闲鱼无官方商家 API，自动化只能到「填到预览为止」

## 浏览器发布链路的硬约束（2026-11-05 实测，踩过才写下来）

- **类目必须按平台预测定，不按搜索第一个候选**。`sell/ai/category.htm` 搜产品名给出的候选叶就是平台自己的归类；
  搜「switch」的第一个候选是 `switch主机贴膜`（配件叶），点它 = 类目错放，平台文案自陈可能「流量损失或下架处罚」。
- **主机类叶子会红字提示适用形态**（如 `家用游戏机` 提示「不包含掌上游戏机」）；两用机按平台预测归 `家用游戏机`，
  不要自己选 `游戏掌机`。
- **切换类目会新冒出必填**：品牌选定后才出现「型号」，「确定」在此之前恒 disabled；切换后还有二次确认
  「可能将导致已填写内容的丢失」。实测标题/价格/库存/主图保住，**类目属性被清空**，必须按新叶重填。
- **必填属性有两种词形，填错服务端判空**：枚举型（如 `最大输出分辨率` 只有 1080p/1440P/2160p/4320P/720p）
  必须点选项，写自由文本 `3840x2160` 会被判空；`生产企业` 下拉常不出候选，要用真实键盘事件写入规范词形
  （`索尼（Sony Interactive Entertainment）` / `任天堂（Nintendo）`），原生 setter 不生效。
- **详情（图文描述）在发布页内就可编辑**，不是只能去旺铺：`宝贝详情` 模块有 清空/添加/图片/文字/高级编辑，
  模块 hover 有 编辑/替换/删除/向后添加图片。平台规则：详情为空时提交会用主图自动填充，**一旦手工添加过，
  删除后就不再自动填充**——换图只能手工删旧加新。
- **主图组只灌空槽位**，换图要先 `--clear`（逐张 hover→删除，以「已填数下降」为准）；
  素材面板里 `filter({hasText: 文件名})` 会匹配到整块网格从而永远点第一张，要从文件名节点走
  `ancestor::*[contains(@class,'PicturesShow_main__')][1]` 回到卡片本体。
- **面板未真开时 `frames()` 会拿到遗留的隐藏 iframe**，此时点它的「确定」可能落到页面底部的「提交宝贝信息」上，
  造成误提交。操作前必须确认 iframe 内 `body.innerText` 有内容。
- **二手商品图只放两类可核实内容**：厂商公开参数、卖家自己的交易条款，并在图内标注「非本机实拍」。
  成色/随附清单这类本机属性不写进图——那些只能由实拍证明。套装版渲染图不得用于单机商品（暗示含游戏卡＝图文不符）。

## 发布之后必须落台账（别只发不管）

发布成功只是起点。线上现状要有一个**由回读生成**的台账，而不是聊天记录或手抄表格：

| 东西 | 落在哪 | 谁写 |
|---|---|---|
| 要发什么（内容计划） | `tools/taobao-publish/packs/<sku>.json` | 人/Agent 起草 |
| 线上是什么（现状台账） | `shop/catalog/items.json` | `catalog.mjs` 回读生成 |
| 缺口与待办（含未证实项） | `items.json` 的 `manual` 块 | 人写，脚本重跑时原样保留 |
| 交易/评价/售后/活动 | `shop/{orders,reviews,aftersale,campaigns}/` | 各域自治，跨域只用 `sku`/`item_id` 关联 |

刷新：`node tools/taobao-publish/catalog.mjs --cdp 9222`（读卖家中心列表 + 逐个编辑页回读类目/图集/宝贝类型 + 合并内容包）。

纪律：

- 每次上架、改价、改类目、换图后**重跑一次**，实测字段不许手改。
- `manual.gaps` 里凡是「已对买家可见但未证实」的条目（实物参数、成色、配件清单），
  优先级高于任何新功能——它们是纠纷与违规的直接来源。
- 台账只登记自有 SKU（按商家编码前缀过滤），店铺历史商品不入。

## 二手主机 SKU 标准（对齐头部竞品，实测得出）

竞品把二手主机做成「**一机型一链接 + 销售属性矩阵**」（实测 24–86 个 SKU/链接），
而不是每档一个链接。用淘宝标准销售属性四维，别自造字符串字段：

| 维度 | pid | 用法 |
|---|---|---|
| 颜色分类 | 1627207 | 载体维度：`机型 + 成色 + 包装/礼包` 全写在值名里，**每个值配一张 SKU 图** |
| 套餐 | 5919063 | 单机标配 / 套餐一 / 套餐二 |
| 版本类型 | 122216431 | 中国大陆 / 日版 / 港版 / 海外版 |
| 内存容量 | 20105 | 单一值（825GB / 1TB / 256GB） |

值名语法有规则不是文风：`（1TB）PS5Slim光驱版【99新】 （送礼包）`、`（99新）NS2主机 带包装+送礼包`。
**只有全新/基本全新才写「带包装」**，99新及以下只写「送礼包」——这是在如实描述有没有原盒，
而「有没有盒子」是买家最高频问题。

定价口径（2026-11-06 定）：**价格与档位完全照抄头部竞品**——档位用竞品在售的那些档，
挂牌价=竞品同格实测价，底价=挂牌价。实测确认竞品页面显示价 == sku2info 挂牌价（无券差），
所以「抄定价」不存在两层价歧义。竞品实测阶梯：相邻成色档 +50、套餐一 +30~+300、套餐二再 +80~+340、
港版比海外版 +30、尾数一律取 8。

三条踩坑提醒：

1. 折扣系数由**这台已经在线上的真实价**反推，别用固定百分比套全阶梯，
   否则生成一套和线上打架的价（实测同一店两台机器姿态能差 11 个点）。
2. 抄竞品价格要接受它的不单调（实测「9新 = 99新」同价），不要为了好看插自造档——
   插了就会与竞品档位对不上，后续比价、调货、回收三方都错位。
3. 完全照抄竞品价 ⇒ 底价=挂牌价，活动域里「实付价不得击穿 floor」等价于「不做降价类活动」；
   同时放弃低价切入，转化只能靠信任标签与配图，这两项从建议升级为必须。
4. 铺多档成色的硬前置是**每档一张 SKU 图**。竞品 13/13、12/12、6/6 全配图；
   用同一张官方渲染图配不同成色，就是新的图文不符。

## SKU 矩阵编辑器：可以自动化，但有两个反直觉的坑（2026-11-06 实测攻克）

入口是销售信息区「+ 创建规格 / 编辑规格」→ 右侧 `.next-drawer`。选「分层展示·选择标准属性构建规格」，
属性最多 **3 个**（头部竞品用 4 个维度，这个入口给不了，别以为是自己没配全）。

两个会让人误判成功的坑：

1. **增行必须按 Enter**。`button.add` 的解禁依赖 React 收到提交；只 `fill()` 不回车，
   值只停在 DOM，「+」点不动，看起来像"平台限制"其实是没有提交。
2. **表格里的 `input.value` 回读会骗人**。价格/数量框只按 Enter 时，**最后一行提交不进去**：
   回读显示 99，提交后落库 0，总库存直接少一档。必须强制 blur（焦点挪回本行另一框再挪到表头），
   并且**判据换成「总库存」这个 React 派生值** —— `总库存 == 档数 × 每档数量` 才算真落库。
   最终复核要读买家页 `skuBase` 的 `props/skus`，不是看提交返回"成功"。

另外：值名有「16 个汉字 / 32 个字符」的**主色+备注合并长度限**，长值名要按空格拆成
主色 + 备注两段（平台展示时自己拼回，与竞品原文一致）；`#struct-p-<pid>` 这类 id 在页面里会重复出现，
AI 助手引导层还会另开一个 `.next-drawer`，所以定位要用文档级 `:visible` + `evaluate` 读状态，
别用 `.last()` 猜哪个抽屉是对的。

「添加图片」是可勾选项 —— **纯文字 SKU 平台接受**，但竞品每个属性值都配图，
不配图意味着买家点不同档位看到的还是同一张图，属观感与转化损失，不是合规问题。

## 上架之后的自迭代循环：体检 → 找差距 → 修 → 复验（2026-11-06 跑通）

发出去只是起点。固定四步，每步都有命令，不靠记忆：

```
node catalog.mjs   # 1 用线上回读重写台账 items.json（含 sku_tiers 逐档价/量/编码/图数）
node audit.mjs     # 2 按判据出 shop/catalog/audit.md（✓/⚠/✗ + 证据 + 修法）
                   # 3 红项里「本轮可自动修」的当场修，「需人工/需决策」的一律不动
node audit.mjs     # 4 复验——同一条判据必须再看一次，改没改要以回读为准
```

判据的三条纪律（不遵守报告就会自欺欺人）：

1. **落库口径读 `window.Json.models.formValues`，不读 DOM input**。编辑页把服务端表单初值注入成
   `window.Json`（脚本标签，不随输入变化），`sku[]/stuffStatus/quantity/outerId/title` 都在这里。
   DOM 回读曾经显示数量 99 而落库 0 ——「过程态」不能当「已上线」的证据。
2. **每一项要么有实测取数方式，要么明写「需人工/本轮未取数」**。判不了的项不许打勾；
   「宝贝类型=二手」这种看着必然成立的字段，也要给到 `stuffStatus.value=6` + 控件 `aria-checked` 这种可核证据。
3. **「可自动修」只收真有命令可跑的红项**。含「需决策」字样的（改标题口径、重设让利下限、删全新档）
   一律归到人那边去，脚本不代替业务签字。

已经跑出来的两类隐蔽失真（值得进判据库）：

- **档位价改了之后，旧的 floor 会被击穿**：`price_ladder.floor` 是人工审批的最低价，
  照抄竞品价以后 `起价 < floor` 就成了「未经确认的降价」——台账要显式标出，别让它静默失真。
- **台账自己会过期**：`items.json` 与线上必须逐档比对（价/量/编码），过期台账会让订单、评价、
  售后三个域的对账全部错位。修法只有一条：重跑 `catalog.mjs`。

## 店铺级判据也不该写「需人工」：体检页与买家页都可读（2026-11-06 实测）

- **入口靠菜单发现，不要猜 URL**：千牛「店铺」菜单里就有 `店铺体检 → /home.htm/health-center-q/`、
  `退货宝`、`真实体验分`、`层级与权益`。同一页可读：待处理违规预警/待处理违规/待处理经营风险/
  全部违规/违规宝贝/受限权限/是否扣分/淘信用/营商保障已开启防控数与已生效拦截策略数。
- **「违规宝贝 N」是历史累计**，不等于在售商品有问题；且**简约智能版里这格点了不跳明细**
  （卡片 `cursor:pointer` 但 URL 不变，实测）。要逐条得切完整版，或用体检页工具箱的「商品合规预检」。
  拿不到明细就把判据写成 ⚠ 并说明为什么，不要标成 ✓，也不要笼统写「需人工」。
- **服务承诺以买家页为准，不看后台勾选**：编辑页 `#sell-field-sevenDaySupport` 的复选框是未勾的，
  但买家页确实显示「七天退货」——判据要落在买家看得到的标签上（七天退货 / 24·48小时内发货 / 运费险），
  并把 `purchaseTips` 里写的时效与标签**做双向一致性检查**（文案 48 小时、标签 24 小时＝自打嘴巴）。
- `formValues.startTime.shelfTime` 是**最后一次提交**时间，不是首次上架时间，别拿它当 `live_at` 写台账。

## 图集一致性用「图片 ID 指纹」判，不靠肉眼回忆（2026-11-06）

上传过的图在 alicdn 上会被改名（`O1CN01…!!<userid>.jpg`），**原文件名在线上不可见**，
所以「这张是不是当初那张」只能靠 ID 比对：

- `catalog.mjs` 把 `media.image_ids`（现主图 ID 集合）与 `media.detail_image_ids` 写进台账；
- `audit.mjs` 两条判据：**详情图 ⊆ 主图集**（否则说明详情是平台自动填充的旧素材或残留），
  **主图 ID == 台账指纹**（有人换过图就必须显式确认，而不是默默失真）。

为什么要专门判这个：平台在**详情为空时会按主图自动生成详情**，而「添加后删除不会自动重算」——
换主图、删误导图之后，详情里可能还留着旧图。这类"改了 A 不影响 B"的平台行为，只能靠指纹比对兜住；
画面内容是不是真的误导（例如套装盒图暗示含游戏）仍需要人眼，脚本只保证**素材来源可追**。

## 改标题这一类动作的三个实测坑（2026-11-06）

1. **长度以页面计数器为准，不以我们的估算为准**。`宝贝标题` 与 `SKU搜索标题` 都是 60 上限，
   平台自己的 `n/60` 计数器才是判据——按「1 汉字=2 字符」估会估低（实测我们算 49、平台报 61/60）。
   写完直接读计数器，超了就不点确定。
2. **提交失败后必须重载编辑页**。失败的那次提交把被拒的值留在了那个标签页的状态里（页面不刷新），
   之后所有 `submit` 都拿着旧值重复报同一个错——表现是「明明已经改对了却还报错」。
   判据：`audit.mjs` 比对 编辑页 `formValues.title` 与买家页标题，不一致就是草稿与线上分叉了。
3. **已填过的档位没有「去填写」入口**。SKU 搜索标题空档显示「去填写」，填好后显示标题文字本身，
   想改就得点单元格；工具要同时支持两种入口（`--force` 重填）。

另外两处结构差异值得记住：发布页第 3 组是**白底图**（1 槽，DOM 里没有任何标签文本，只能按序号 `--gi 2` 定位，
且白底图规范不接受叠字，用官方单机渲染而不是信息卡）；档位级搜索标题走
`.next-drawer` 详情抽屉，面板里 `input[0]=SKU搜索标题`、`input[1]=价格`、`input[2]=数量`、`input[3]=商家编码`。

**第 5 步是收尾，不是可选项**：`node tools/taobao-publish/tabs.mjs --close`。CDP 接管的是用户可见的窗口，
脚本自己开的标签页断开连接也不会消失，堆在那儿就是给别人留垃圾（2026-11-06 被明确反馈过一次）。
工具层的规矩是「谁 `newPage()` 谁负责关」，复用别人已打开的页面则不要关；
注意 `process.exit()` 会跳过 `finally`，dry-run/失败分支要自己关。
**别关到剩 0 个标签页**——那样 `connectOverCDP` 会报 `Browser context management is not supported`，
自己把门锁上（`tabs.mjs --close` 已内置保留 1 页的保护；恢复用 `curl -X PUT "http://127.0.0.1:9222/json/new?<url>"`）。

## 改「七天退货」这类服务开关：三个同名模板行 + 一个极性坑（2026-11-06 实测）

- 发布页**同时渲染三行**：`#sell-field-sevenDaySupport`（必须支持，hidden+disabled）、
  `#sell-field-sevenDayNotSupport`（不支持，hidden+disabled）、`#sell-field-sevenDayOptional`（可支持，**唯一可点**）。
  按文字「七天退货」去定位会命中禁用行 —— 我的 `--bool` 第一版就是这样：没点到任何东西，
  却因为回读到 `checked=false` 而打印了 ✓。**假阳性的根源是"用当前状态当操作结果"**。
  规矩：定位一律用元素 id；只接受「可见 + 有尺寸 + 未 disabled」的控件；
  日志要同时给出 `before` 与 `after`，两者相同就明写「本来就是这个状态，未点击」。
- **买家页判服务要看极性**：关闭后页面文案是「退货宝不支持7天无理由退货」，
  裸正则 `/7天无理由|七天退货/` 依然为真。判据必须先用 `不支持…` 反向排除，再判存在。
- **类目给的是「可支持」= 卖家可选**，不是强制（强制那一行是隐藏禁用态）。所以开/关都合规，
  但**质量与描述不符的退货义务不因关闭而减少**，运费责任仍按判定结果走。
- 关服务属于「改一处要同步三处」：`sell-field-sevenDayOptional` 勾选、`购买须知`(purchaseTips)、
  内容包 `detail`/`purchase_note`（以及据此生成的详情图文字）。任一不同步就是自相矛盾的描述。
  `audit.mjs` 现在有两条判据盯着：策略 vs 标签、须知 vs 标签。
